Complementa `02-plano-aplicacao.md`. Rollback aqui é descrição; nenhum comando foi rodado no projeto operacional.

## 1. Estratégia geral de rollback

1. Ponto de restauração: anotar a hora UTC imediatamente antes da primeira migration e o identificador do backup lógico (`supabase db dump`, `docs/backup-restore-procedure.md`) e do PITR, se o plano do projeto o oferecer (confirmar no painel; não verificável por esta leitura).
2. Cada arquivo é uma transação: falha no meio não deixa estado parcial naquele arquivo. O rollback só é necessário para migrations já concluídas.
3. Ordem: sempre inversa à de aplicação. Antes de qualquer `drop`, confirmar que nada novo gravou dados nas tabelas (contagem de linhas) e que as flags de envio e o agendador estão desligados.
4. Tabelas novas ainda vazias: `drop table ... cascade` seguro. Depois de uso real: preferir desligar a funcionalidade (flag/UI) e manter o dado; restauração de backup só por decisão do dono (perde o que foi gravado depois do ponto).
5. Funções redefinidas: restaurar com a definição capturada pré-janela (`02` seção 6); conferir ACL com o snapshot (`capture-acl-snapshot.mjs`) e hash de corpo.
6. Hotfix `record_risk_alert_action`: NUNCA deixar a versão pré-hotfix no ar. Rollback de qualquer migration da onda B/D que redefina essa função deve terminar com o corpo de md5 `930f6d75898793479b418950b0053bd9`.
7. Registro de histórico: reverter também a linha de `schema_migrations` se tiver sido inserida (mesmo cuidado do `02` seção 5).

Classes: "reversível" = desfaz sem perda de dado legítimo; "reversível antes do uso; irreversível depois" = cria tabelas que, uma vez com dados, só voltam via backup; nenhuma migration pendente apaga dados existentes (sem `drop table`/`truncate`/`delete` de dados nos arquivos).
