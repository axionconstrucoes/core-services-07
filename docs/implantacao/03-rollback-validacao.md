# 03 - Rollback por migration e validação pós-aplicação (PLANO; nada foi executado)

Complementa `02-plano-aplicacao.md`. Rollback aqui é descrição; nenhum comando foi rodado no projeto operacional.

## 1. Estratégia geral de rollback

1. Ponto de restauração: anotar a hora UTC imediatamente antes da primeira migration e o identificador do backup lógico (`supabase db dump`, `docs/backup-restore-procedure.md`) e do PITR, se o plano do projeto o oferecer (confirmar no painel; não verificável por esta leitura).
2. Cada arquivo é uma transação: falha no meio não deixa estado parcial naquele arquivo. O rollback só é necessário para migrations já concluídas.
3. Ordem: sempre inversa à de aplicação. Antes de qualquer `drop`, confirmar que nada novo gravou dados nas tabelas (contagem de linhas) e que as flags de envio e o agendador estão desligados.
4. Tabelas novas ainda vazias: `drop table ... cascade` seguro. Depois de uso real: preferir desligar a funcionalidade (flag/UI) e manter o dado; restauração de backup só por decisão do dono (perde o que foi gravado depois do ponto).
5. Funções redefinidas: restaurar com a definição capturada pré-janela (`02` seção 6); conferir ACL com o snapshot (`capture-acl-snapshot.mjs`) e hash de corpo.
6. Hotfix `record_risk_alert_action`: NUNCA deixar a versão pré-hotfix no ar. Rollback de qualquer migration da onda B/D que redefina essa função deve terminar com o corpo de md5 `930f6d75898793479b418950b0053bd9`.
7. Registro de histórico: reverter também a linha de `schema_migrations` se tiver sido inserida (mesmo cuidado do `02` seção 5).

Classes: "reversível" = desfaz sem perda de dado legítimo; "reversível antes do uso; irreversível depois" = cria tabelas que, uma vez com dados, só voltam via backup; nenhuma migration pendente apaga dados existentes (sem `drop table`/`truncate`/`delete` de dados nos arquivos).

## 3. Validação pós-aplicação (por onda e final)

Executar com acesso de leitura; registrar a saída em arquivo fora do repositório (sem dados pessoais).

1. Histórico/contagem: `select count(*) from supabase_migrations.schema_migrations;` (esperado: 134 + as aplicadas na janela + a linha do hotfix, se registrada) e conferir nomes por `name`.
2. Hotfix preservado: `select md5(replace(prosrc, chr(13), '')) from pg_proc p join pg_namespace n on n.oid=p.pronamespace where n.nspname='public' and proname='record_risk_alert_action';` = `930f6d75898793479b418950b0053bd9`; `prosecdef = true`; `proconfig` contém `search_path=""`; `has_function_privilege('anon', oid, 'EXECUTE') = false` e `'public'` idem.
3. Superfície `anon`: nenhuma função SECURITY DEFINER nova com EXECUTE para `anon`/PUBLIC (`aclexplode(proacl)` sobre `pg_proc` do schema public); comparar com o snapshot de ACL.
4. RLS: toda tabela nova de `public` tem `relrowsecurity = true` (`select relname from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname='public' and relkind='r' and not relrowsecurity;` deve listar só exceções conhecidas).
5. Consultas por migration: coluna "Verificação" da seção 2.
6. SLA: `select risk_level, count(*) from public.sla_matrix_rules where is_active group by 1;` sem duplicidade ativa; se a 177000 foi aplicada, conferir 2 e 5 dias úteis; se não, conferir que continua 1 e 3 (e registrar a divergência com o aprovado).

Smoke tests (aplicação, modo piloto, sem envio real): login; abrir um projeto; Qualidade e Seguros/Garantias abrem sem erro de permissão (somente leitura); Painel de Alertas lista; abrir uma ação SLA e verificar prazos; `/api/cron/risk-alerts` em modo seco (`risk-alerts-weg-dry-run`) sem criar outbox para destinatário real.
